## Investigated 2026-08-13 -- blocked by a ledger-model limitation, not analysis

Both suggested references disproved by the element-size check: the disassembly
pushes 0x74 (116) to the vector dtor iterator, while
`MixFileCreator::FileInfoStruct` is 0x10 and `ProxyClass` is 0x34. Both are the
structural-boilerplate false positive -- see 001b1480.md for why that shape
scores high regardless of class.

The real owner is almost certainly the 0x74-byte BFME variant of
`VehicleCurveClass::_ArcInfoStruct` (the one WITH a non-trivial destructor):
this target sits immediately before the already-matched
`?Add@?$DynamicVectorClass@U_ArcInfoStruct@VehicleCurveClass@@@@...` row at
0x009347C0, which independently established sizeof(T)==0x74 for that exact
second-copy class.

THE BLOCKER IS NAMING. The mangled name
`?Clear@?$VectorClass@U_ArcInfoStruct@VehicleCurveClass@@@@UAEXXZ` is already
claimed at a DIFFERENT address (0x0000B9CE, VectorClassClearSplineThunk.cpp) --
a 5-byte JMP thunk shared by trivially-destructible types, which is what the
52-byte header `_ArcInfoStruct` (no dtor) folds to. add_match enforces
one-name-one-address, so a second row under that name cannot be claimed.

Two genuinely distinct BFME classes share one mangled name because the vendored
header defines only one of them. Resolving this needs a ledger-level decision
about representing both, not a source-level fix. Do NOT invent a different class
name to make the arithmetic pass.
