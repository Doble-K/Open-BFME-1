## Investigated 2026-08-14 -- reference function is provably WRONG

The suggested `?newMap@W3DTerrainLogic@@UAEX_N@Z` cannot be this body.

Zero Hour's newMap is two calls:

    TheTerrainRenderObject->loadRoadsAndBridges( this, saveGame );
    TerrainLogic::newMap( saveGame );

The first of those is a __thiscall on a singleton with two stack arguments.
What retail actually does first is

```
    8b 46 10   mov  eax,[esi+0x10]      ; a member of this
    57         push edi                 ; the Bool argument
    50         push eax
    e8 ...     call ...                 ; ILT 0x00021B7A
    83 c4 08   add  esp,8               ; __cdecl, two arguments, no this
```

and ILT 0x00021B7A resolves to body **0x004BBCF0**, which is already claimed
as **`?GadgetProgressBarSetProgress@@YAXPAVGameWindow@@H@Z`** -- a free
function taking (GameWindow*, Int). The shapes do not match and the callee is
not loadRoadsAndBridges.

Two more things point the same way:

- the packet's other pin, 0x090D9964, is past the end of the image; it is not
  an address at all.
- this body sits at 0x00491550, 0x90 bytes after an unclaimed 109-byte body
  at 0x004914C0 that the second call reaches, and its neighbourhood is load
  screen code -- 0x00490A00 `?processProgress@MultiPlayerLoadScreen@@UAEXHH@Z`
  and 0x00490CC0 `?processProgress@GameSpyLoadScreen@@UAEXHH@Z` are both in
  the queue nearby.

So this is a load-screen method that reads a GameWindow* from a member at
+0x10, drives a progress bar with it, and forwards to a sibling at
0x004914C0. Whoever picks it up should start from the two processProgress
packets rather than from W3DTerrainLogic.

Note W3DTerrainLogic::init and ::reset *were* converted from packets 006be0e0
and 006be110, so the class itself is real and its layout is pinned -- it is
only this address that is misattributed.
