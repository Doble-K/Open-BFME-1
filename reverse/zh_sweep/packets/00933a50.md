## Investigated 2026-08-13 -- 62 of 157 bytes; two findings, one still open

The first 62 bytes reproduce exactly from render2d.cpp's existing
Set_Coordinate_Range. The remaining 95 are Update_Bias, which retail
**inlines** -- there is no `call` anywhere in the body.

**Getting it to inline at all takes two changes.** Update_Bias is defined
*after* its caller in render2d.cpp, and MSVC cannot inline a definition it
has not seen; moving it above is necessary but not sufficient, because /O2's
own heuristic still declines it. `__forceinline` on the definition does it.

**BFME has no BiasedCoordinateOffset.** With Update_Bias written as ZH has
it -- `BiasedCoordinateOffset = CoordinateOffset; ... BiasedCoordinateOffset
+= bais_add;` -- the compiled body copies +0x0c/+0x10 out to +0x14/+0x18 and
then works on +0x14/+0x18. Retail does neither: it has no copy, and its last
four instructions are

    d8 41 0c   fadd  DWORD PTR [ecx+0x0c]
    d9 59 0c   fstp  DWORD PTR [ecx+0x0c]
    d8 41 10   fadd  DWORD PTR [ecx+0x10]
    d9 59 10   fstp  DWORD PTR [ecx+0x10]

biasing CoordinateOffset **in place**, in the same two slots
Set_Coordinate_Range just wrote. Rewriting Update_Bias to
`CoordinateOffset += bais_add;` makes that tail match exactly, and the other
twelve matched rows in render2d.cpp still verify.

**Still open**, and the only thing between this and a match: retail's biased
branch is 19 bytes longer than the rewrite produces (`je +0x51` against
`je +0x3e`). Both compute the same thing from the same two globals --
0x012D6DB4 and 0x012D6DB8, the screen width and height, read directly as
signed ints with the usual `test`/`jge`/`fadd 2^32` unsigned fixup -- so the
difference is in how the two `* 0.5f` / `* -0.5f` scalings are folded against
the divide, not in what is computed.

Nothing was landed and render2d.cpp is unchanged; a 62-of-157 reconstruction
is not a match. Whoever picks this up should start by reapplying the two
changes above.
