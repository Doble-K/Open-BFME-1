The packet's only candidate, `DecalMeshClass::DecalMeshClass(MeshClass*,
DecalSystemClass*)` in decalmsh.cpp, is already present in-tree with a
present-unmatched marker. Ported unchanged it fails on exactly ONE byte:

Why that is a contradiction and not a codegen nuance:

- WWASSERT is a release no-op, and there are no calls in this body at all

- RefCountClass's own default constructor is independently verified matched
  elsewhere in this binary (RVA 0x005F38A0, exact match) and writes NumRefs = 1
  unconditionally.
- There is no public API or additional call through which DecalMeshClass's
  constructor could legitimately zero that field afterwards.

So the vendored candidate cannot be the source of these bytes. The 96.9%
agreement is misleading -- the disagreement is a single semantically decisive
byte.

Either the real owner is a different class whose base does not bump a refcount,
or BFME's DecalMeshClass does not inherit RefCountClass at all. Establish which
before attempting again; do not force the byte with a placeholder base.
