## Investigated 2026-08-13 -- reference class is provably WRONG

The suggested `??0GeometryInfo@@QAE@ABV0@@Z` cannot be this body.

- That symbol is **already matched**, at 0x003A6360, **24 bytes**, from
  Object.cpp compiling the vendored ZH `Common/Geometry.h`.
- This body is 57 bytes and its first instruction after the prologue is
  `mov DWORD PTR [eax],0x11129b4` -- a vtable pointer store. A GeometryInfo
  that stored one could not also produce a 24-byte copy constructor; 24 bytes
  is a plain block copy of a POD, which is what a *non*-polymorphic
  GeometryInfo compiles to.

Three retail offsets agree with the non-polymorphic reading, in ZH's field
order, and none of them leaves room for a vptr:

- 0x0087F160 `parseGeometryIsSmall` writes m_isSmall at store+0x04
- 0x001E1A30 `getFiringLineOfSightOrigin` takes &m_geometryInfo as Object+0xac
- `reference/shims/bfmeobject` records m_minorRadius read at Object+0xbc,
  i.e. +0x10 inside the geometry -- the fifth dword with no vptr, and it
  reconciles the shim's `0x0a8` note to the 0xac the retail body actually uses

So: m_type 0x00, m_isSmall 0x04, m_height 0x08, m_majorRadius 0x0c,
m_minorRadius 0x10, and 0x20 bytes total with no vtable.

WHY THE 96.5% IS MISLEADING: a compiler-generated copy constructor for any
polymorphic class of this size is the same shape -- store vtable, copy N
dwords, `ret 4` -- and the vtable address is a relocation, so it is excluded
from the comparison. The only distinguishing operand is therefore invisible to
the metric. Same systematic false positive the 001b1480 packet documents for
vector deleting destructors.

Open question for whoever picks this up: the vtable at 0x011129B4 is the
discriminator and is not in `reverse/vtables.tsv`. Identify its owner -- some
polymorphic class of exactly 0x20 bytes with seven dword members -- and the
name follows. Do NOT land it as GeometryInfo.
