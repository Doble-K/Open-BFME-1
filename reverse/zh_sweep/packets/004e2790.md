## Landed 2026-08-15 -- the earlier verdict below was wrong

This body IS reachable from source and is now matched at 0x004E2790 from
`Code/GameEngine/Source/GameClient/GUI/GUICallbacks/Menus/ScoreScreen.cpp`.

The register convention was never the obstacle. MSVC does give this `static`
function a private eax/edi convention -- that part of the analysis was right --
but it gives it the *same* one when compiling the Zero Hour source here, so the
prologue reproduces itself. Compiling the reference body unchanged already
landed 54 of the 55 bytes. The single divergence was `ff 50 0c` against retail's
`ff 50 14`: BFME makes `GameInfo::getLocalSlotNum` virtual at slot 5, where the
vendored header declares it a plain inline member. That is the same fact the
`updateChallengeMedals` conversion (packet 004e27e0) pinned earlier the same
day, and applying it here closes the body exactly.

The fix is a TU-local facade class with the slot in the right place. A
pointer-to-member cast does not work: it emits `mov eax,[eax+0x14]` and an
indirect call through the register, where retail calls straight out of memory.

Lesson for the next reader: a mangled name that disagrees with the observed
convention is not proof the body is unreachable, because the compiler applies
the same private convention to the same `static` declaration. Check what the
reference source actually compiles to before concluding anything from the
mangling.

### Superseded analysis, kept for the record

The name is almost certainly right and the body is provably not reachable from
source. Retail takes both arguments in registers:

    4e2790: push esi
    4e2791: mov  esi,eax          <- first argument arrives in eax
    ...
    4e27a6: cmp  edi,eax          <- second argument is live in edi on entry
    4e27ad: ret                   <- no stack arguments, no cleanup

Nothing in the 55 bytes touches `[esp+N]`. The lead's mangled name
`?isSlotLocalAlly@@YA_NPAVGameInfo@@PBVGameSlot@@@Z` is `YA` — __cdecl, stack
arguments — so the two cannot both be true. This is MSVC 7.x giving a `static`
function a private register calling convention because every call site is
visible in the translation unit; the Zero Hour source does declare it `static`.
There is no source spelling that reproduces it: __fastcall passes in ecx/edx,
not eax/edi, and it would still be a different mangled name.

Checked the boundary before assuming: 0x004E2774 is `c3` followed by int3
padding to 0x004E2790, so this is a real function start and not a mis-split
tail. The block is otherwise unremarkable — the body matches the Zero Hour
source line for line.

Land it only if this tree gains a way to pin a calling convention per row.
Do not spend another session on the source spelling.
