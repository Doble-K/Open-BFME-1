## Investigated 2026-08-13 -- reference class is provably WRONG

This is a standard MSVC vector deleting destructor (`??_E<T>@@QAEPAXI@Z` shape).
The suggested reference `??_EPivotClass@@QAEPAXI@Z` cannot be right:

- retail pushes elemSize `0x88` (136 bytes) for the `??_M` iterator call
- `sizeof(PivotClass)` is `0xB4` (180 bytes), derived from this repo's OWN
  byte-verified `??0PivotClass@@QAE@ABU0@@Z` at 0x00972D70, whose field copies
  run through 0xB2

WHY THE 98.8% IS MISLEADING, and this generalises to the whole packet tier:
a vector deleting destructor is generic boilerplate -- `push` flags, `test`,
call `??_M`, conditional call `??_V`/`??3` -- identical for EVERY class using
vector new/delete. The only distinguishing bytes are the size literal and the
destructor address, and the address is excluded from the comparison as a
relocation. So near-identical scores here carry almost no evidence about which
class it is. ALWAYS sanity-check the pushed element size against `sizeof` of
the candidate class before trusting a high score on a boilerplate shape.

Also decoded: the embedded dtor pointer 0x0043DC2B -> RVA 0x3DC2B resolves via
jump-thunk `?j_0003dc2b` to a bare `ret` at 0x1B1200 (an empty non-virtual
destructor), but that address has no ledger row and a full .text CALL/JMP rel32
scan found no direct callers, so it yields no class identity. A byte-pattern
scan confirmed this exact push-0x88 shape is unique in the binary, so there is
no COMDAT-folded twin to borrow a name from.

Open question for whoever picks this up: identify the 136-byte, trivially
destructible, non-virtual class. Cross-referencing array-new sites of a
136-byte type is the suggested route. Do NOT land it with a fabricated
same-sized placeholder class -- that is not a reconstruction.
