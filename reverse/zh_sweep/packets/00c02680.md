## Investigated 2026-08-14 -- not one function: four ICF-folded entries

The premise is false. This address is not unclaimed, and the 51-byte window does
not correspond to any single function. The range holds FOUR separate entries,
each already carrying its own matched row:

- 0x00C02680  8B   adjustor thunk to a GameInfo dtor (via 0x374D4)
- 0x00C02688  11B  adjustor thunk at +0x60 to a Snapshot/AsciiString dtor (0xD828)
- 0x00C02693  22B  real body: pushes constants, adds +0x6c, calls 0x9F6D76, ret
- 0x00C026A9  14B  adjustor thunk at +0x9c, jmp

Summed span is 55 bytes (0xC02680-0xC026B7), which EXCEEDS the packet's 51-byte
window -- so the window is also truncated mid-instruction, cutting off the final
jmp's rel32 displacement and leaving only the 0xE9 opcode visible.

Every byte here is already backed by a matched ledger row. Converting those four
gen_asm rows into real C++ thunks is a legitimate task, but it is a gen_asm
cleanup, not "claim an unclaimed function". Do NOT invent a single 51-byte
function to fit a boundary that does not exist in retail.
